# 向后兼容核查 SOP

在存量仓库里，改动最大的风险不是新逻辑写错，而是**破坏了既有的调用方**。
AI 倾向于「把接口改成它认为更好的样子」，对仓库里沉默的调用者毫无感知。本 SOP 给
contract 角色（设计时）与评审角色（复核时）提供双保险核查流程。

## 识别信号

- 公开函数/类的签名变更：删参数、改参数名、改参数顺序、收窄返回类型。
- 公开符号被删除或改名，且没有保留别名。
- DB schema 变更：删列、改列类型、加 NOT NULL 无默认值列。
- 消息/协议格式变更：字段删除、类型变化、枚举收窄。
- 配置键改名、删除或语义变化；默认行为变更（同一代码路径新旧行为不同）。

## 定位步骤

1. 从 diff 提取全部公开接口变更（导出符号、schema、配置、协议），逐条列出。
2. 全仓搜索每个变更符号的调用点，区分内部调用方与同仓外部调用方（其他模块/服务/脚本）。
3. 对每条变更问：「不修改任何调用方，旧调用方式还能工作吗？」不能即破坏面。
4. schema 变更额外检查「新旧代码共存窗口」：滚动发布期间旧代码能否读写新 schema。
5. 无法确认调用方全集（如对外公开 API、被其他仓库依赖）→ 一律按有外部调用方处理。

## 修复模式

- 新增参数必须带默认值，不得插入到现有位置参数中间。
- 废弃走 deprecation：保留旧符号 + 警告 + 明确移除版本，不直接删除。
- schema 变更用 expand-contract：先加新列（可空/有默认值）→ 双写过渡 → 后清理旧列。
- 配置键改名保留旧键别名至少一个版本；默认行为变更需显式 feature flag 或写入变更日志。
- 确认有破坏面且无法避免 → 标 yellow 交人工评估影响面，禁止静默合入。

## 验证方式

1. 不修改任何既有调用方代码，全量回归测试通过。
2. 破坏性变更清单（允许为空）写入评审记录，每条附影响调用方与处置方式。
3. schema 变更附滚动发布演练或共存窗口论证。
