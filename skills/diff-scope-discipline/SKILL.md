# diff 范围纪律 SOP

AI 的「热心过度」是评审失效的头号原因：一个改一行的任务，交回五百行的 diff——
顺手重构了无关函数、重新格式化整个文件、夹带了三个「顺手改进」。真改动淹没在噪声里，
评审者要么漏看要么放弃。本 SOP 是评审角色的**第一道工序**：范围不合格，不进入实质评审。

## 识别信号

- diff 触及契约 in_scope 之外的文件、模块或函数。
- 大规模纯格式化变更（空白、换行、import 排序）与语义变更混在一起。
- 无关的重命名、重构、「顺手修复」的周边 bug。
- 改动规模与任务明显不成比例（一行任务，百行 diff）。
- out_of_scope 中显式声明不动的区域出现改动。

## 定位步骤

1. 取出契约的 in_scope / out_of_scope 清单作为基准。
2. 逐 hunk 过 diff，每个 hunk 三分类：**必需**（可追溯到某条 acceptance）/ **噪声**（纯格式化）/ **夹带**（真实改动但与任务无关）。
3. 统计比例：噪声 + 夹带 hunk 占比；out_of_scope 区域命中数。
4. 对每个「必需」hunk 反查：它能对应到哪条 acceptance？对不上就降级为夹带。

## 修复模式

- 夹带改动：**打回 author 拆分**——无关改进应单独提交、单独评审，不在本 run 内夹带。
- 格式化噪声：要求与语义变更分离提交；仓库无格式化基线的，建议先落地格式化基线再评审。
- out_of_scope 命中：直接 red（违反冻结契约），无折中。
- 占比阈值：噪声 + 夹带超过 diff 总量约 20% 即打回，不在噪声中做实质评审。

## 验证方式

1. 打回后重交的 diff：每个 hunk 可追溯到 acceptance 条目，out_of_scope 零命中。
2. 评审记录中保留范围分类统计（必需/噪声/夹带数量与占比），供 postmortem 复盘。
3. 同一 author 重复夹带 → postmortem 沉淀为提示词/流程改进，而非个案处理。
